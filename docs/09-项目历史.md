# 09 · 项目历史

> 从起因到当前的阶段沿革：每个阶段解决了什么问题、做了什么取舍、留下了什么。
> 本文只记录**对产品形态有影响的节点**，不做逐次改动的流水（版本级变更见 [08 · 版本管理](08-版本管理.md#六版本历史)）。

## 〇、起因：把"能跑"变成"能被别人用"

项目起点是一个更大的长期研究计划。方向很清楚，但一个还没被别人用过的能力，
无法证明自己真的成立。于是做了一次收口：

> **先交付一个数学上站得住、任何人今天就能打开来用的实体。**

选择求解器作为这个实体，理由有三个：

1. **正确性可被独立检验** —— 解可以回代验证，对错不靠嘴说；
2. **有明确的边界** —— 能做什么、不能做什么，可以写清楚，不留模糊地带；
3. **有确定的形态** —— 可以做成网页给人用，也可以做成工具给 AI 用，两条路都成立。

这个收口决定了后面所有设计取舍：**宁可范围小、边界清，也不要范围大、说不清。**

---

## 一、阶段一 · 内核成型（2026-08-24，`v1.0.0`）

**做了什么**：把求解内核做成单文件自包含的网页产品，并同时提供 MCP 服务端形态。

- 定下技术路线：**区间算术 + 仿射算术 + 收缩算子 + Krawczyk 认证 + 全局分支定界**。
- 定下产品规格：≤6 变量、默认域 ±1e6、固定 6 位小数、残差三档容差。
- 定下诚实口径：**已验证解数学保真 + 全局穷尽尽力而为**；未穷尽标 `truncated`。
- 一次性说清"不做什么"：不做符号推导、不做 ODE、不做整数强制。

**留下的东西**：一句对外定位——「**同样的题，永远同一个答案。不靠猜，靠算。**」

## 二、阶段二 · 缺陷攻坚（2026-09 上旬，`v1.0.6` / `v1.0.7`）

产品化跑起来后，问题开始暴露，而且暴露的都是**"该有解却报无解"**这类最伤信任的缺陷。

| 缺陷性质 | 表现 | 处理 |
|---|---|---|
| 认证结论不可信 | 数值环节出现 NaN，全局分支却仍报告"已穷尽" | 修：NaN 一律视为不可信，不允许进入认证链 |
| 区间包络不可靠 | 对超越函数做仿射求值时区间塌缩成一个点（区间不再包含真值） | 修：恢复严格包络 |
| 除法系统性假阴性 | 含除法的方程在给定域下**恒报无解**，而真解存在 | 修：仿射求逆的中心双重计数 |
| 舍入误杀真解 | 点域处浮点差（约 2e-16）把真解判成"不在区间内" | 修：给"区间排除 0"加浮点容差（只放宽到不引入假阳性为止） |
| 超时挂起 | 单变量超越/周期方程可能长时间不返回 | 修：扫描加根数与时间护栏，并按结果如实标"无限解集"或 `truncated` |

**这一阶段定下的纪律**（此后一直执行）：

- **`sound` 性质优先于覆盖率** —— 宁可少给一个结论，不可多给一个错的结论。
- **修缺陷优先于加功能** —— 已知会误导用户的缺陷不修完，不加新能力。
- **每个修掉的缺陷都留一条回归测试**（防止同一个坑掉两次）。

## 三、阶段三 · 合规与分发（2026-09-07，`v1.0.8`）

能力稳定后，开始处理"别人凭什么信你、在哪能拿到你"。

- **合规**：网页页脚补双备案号与版权声明，明确运营主体是公司而非个人。
- **诚实上报**：`/health` 不再手写版本号，改为如实上报并回显求解核心自报版本，
  **杜绝"文档说一个版本、程序说另一个版本"**。
- **分发完整性**：npm 包补上 HTTP 服务端入口与备案图标，让"装下来就能开服务"成立。
- **多地一致**：GitHub 仓库、npm 包、生产站点、对象存储镜像四处同步，逐份校验哈希。

**留下的规矩**：**对外可见的版本信息必须能实测核对，不能只写在文档里。**
（这条在后来发现"多处版本常量漏改"时救过一次场。）

## 四、阶段四 · 从"能收费"到"能收到钱"（2026-09-23，`v1.0.9` / `v1.0.10`）

这是产品认知上最重要的一次转折。

**先做的事**：给托管端点加上按次计费与订单、余额、账本。
技术上很快跑通了 —— 但随后发现一个更根本的问题：

> **"能从技术上收费"和"在现实里真的收得到钱"是两件事。**

`v1.0.10` 修的就是这条链路上的断点，而且全都是**非技术性**的：

| 断在哪 | 真相 |
|---|---|
| 付款页要求"必须带订单号才显示收款码" | 而文档、页脚给出的入口恰恰不带订单号 ⇒ **唯一的真人付款入口是死路**。而收款码图片本身无鉴权即可访问 —— 这个限制**对攻击者无效，只挡住了真心付钱的人** |
| 付款说明里写着"邮件确认到账""数日内到账" | 这是更早一版的人工流程残留。它会直接劝退诚心支持的人，也与"付款后立即生效"自相矛盾 |
| 给 AI Agent 的指引说"展示付款链接"，但该字段恒为空 | **Agent 拿不到任何可展示的付款入口**，按步骤执行也走不通 |

**同时定下的机制（`v1.0.9`）**：托管端点改为**信任制 + 自助入账** ——
固定 ¥0.01/次、成功才扣、免费路径写进响应（传 `honorPaid` 即放行）、
付款后由付款方自助入账、**立即生效、零人工**；营收口径诚实分栏，
**"凭声明的额度"与"真营收"从不相加**。

**这一阶段的核心教训**（已写进 [01](01-产品作用.md) 与 [06](06-商业授权与收费.md) 的口径里）：

> 凡是"只挡页面、不挡文件"的限制，收益为零、成本是真实用户；
> 凡是"让 Agent 去展示 X"的指引，先确认 X 在响应里真的非空。

## 七、不变的立场

三个阶段下来，有三条东西从没变，也不打算变：

1. **诚实边界**：算得出就盖章，算不出就明说。不承诺"100% 不漏解"——那在数学上就做不到。
2. **fail-closed**：不确定时拒绝或降级，绝不"猜一个答案假装通过"。
3. **克制扩张**：没有真实信号就不加功能。**少而可靠**优于**多而模糊**。

> 一个工具的价值不取决于它能算多少，而取决于**它说的每句话是否站得住**。

  手机/桌面"添加到主屏幕"即装、离线可用。**不经过 Apple、零费用、零 Apple ID、国内外都能装**。
