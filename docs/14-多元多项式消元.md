# 14 · 多元多项式消元与 suan61 精确求解

> 适用范围：`nvars ≤ 6`，输出**全精度 double**（2026-05 起移除 6 位有限网格），**只给一个解**（不给区间、不给解集）。
> `n > 6` 一律 fail-closed，交回旧路径，**零行为变更**。
>
> 本文只记录**经过实测**的东西。凡是没跑出数字的设想，一律标注「未验证」，
> 不许出现在结论里。

---

## 1. 整体架构

```
多变量多项式方程组 (n ≤ 6)
   │
   ├─ ① grevlex Gröbner 基      快，只用来判零维           ~3 ms
   │
   ├─ ② lex Gröbner 基          构造真正的消元塔           ~4650 ms  ← 当前最大头
   │      ↓
   │   塔尖 = 只含单变量的基元素
   │      ↓
   ├─ ③ 沿塔自顶向下求解
   │      阶段 A：Sturm 序列浅层定位，二分到桶宽 < 1e-3
   │      阶段 B：桶内 Newton + 连分数有理化 + 双重认证
   │      认证失败 ⇒ 回退纯精确深二分 fbExact
   │      ↓
   ├─ ④ 逐层回代 + 原始方程组独立残差复核
   │
   └─ ⑤ box 过滤 → 去重 → 限 maxSol
```

**完备性**：`proof = bezout-saturated` 当且仅当解数达到 Bézout 上界。
未达到就是 `unproven`，绝不把部分结果冒充完整解集。

## 2. lex Gröbner 基（当前瓶颈，占 53%）

### 2.1 实测结构（quad6，c=12，对称二次 6 变量）

| 指标 | 数值 |
|---|---|
| pairs | 300 |
| 剪枝（product + chain） | 156（52.0%） |
| 真正计算 S-多项式 | 144 |
| 轮次 | 19 |
| 最终基 | 18 元素 / 910 个系数 |
| 基系数平均位数 | **6.3 bits**（最大 26 bits） |
| 中间系数峰值 | **128 bits** |

**这张表最重要的一行是最后两行**：最终基的系数极小（6.3 bits），
但**运算过程中的中间系数会膨胀到 128 bits**。

这是 Buchberger 的经典现象 —— *intermediate swell*（中间膨胀）。
它解释了为什么 gcd 是瓶颈：算的不是 6 bits 的数，是 128 bits 的数。

## 3. gcd 三层加速（v10，本轮主要成果）

### 3.1 第一刀：double 快路径

**数学等价性**：若 `0 ≤ a, b < 2^53`，则 double 欧几里得与 BigInt 欧几里得返回**同一个** gcd。

理由：double 精确表示整数到 2^53；欧几里得每步余数严格递减且起点 < 2^53，
故全程无舍入（Knuth TAOCP 4.5.2）。

**实测**：`a,b ≤ 2^53` 的调用占 78.7% 的调用数，但只占 7.1% 的时间。

| 路径 | 调用数 | 耗时 | ns/call |
|---|---|---|---|
| FAST（≤ 2^53） | 3,223,518 | 609 ms | 189 |
| SLOW（含大数） | 872,092 | **7987 ms** | 9158 |

⇒ 快路径覆盖 79% 的调用，只占 7% 的时间。**战场在那 21% 的大数上。**

### 3.2 第二刀：Lehmer 批量 Euclid

**原理**（Knuth TAOCP §4.5.2 Algorithm L）：
取 `a, b` 的高位单精度近似 `(X, Y)`，在**单精度**上把 Euclid 跑多步拿到商序列，
再在**完整精度**一次性兑现。省掉的是"每步一次大整数除法"。

**适用范围**：慢路径操作数实测集中在 48–128 bits，落在 Lehmer 的标准窗口内。

**正确性**：Lehmer 只影响速度。最终 gcd 值由 BigInt 精确收尾计算，
与朴素 Euclid 逐位相同。

### 3.3 第三刀：gcd 缓存（**必须分段启停**）

这是本轮最反直觉的结论。

| 阶段 | 命中率 | 缓存效果 |
|---|---|---|
| lex | **16.8%** | +2.4%（**负收益**） |
| 回代 tower | **68.1%** | −51%（**腰斩**） |

三轮交替实测（quad6）：

| 模式 | total | lex | tower |
|---|---|---|---|
| 缓存 off | 13230 / 13331 / 13229 | 4600 / 4553 / 4698 | 8623 / 8771 / 8526 |
| 缓存 on | 8981 / 9040 / 8870 | 4775 / 4720 / 4647 | 4200 / 4313 / 4216 |

⇒ **正确做法是分段启停**：lex 阶段关闭，回代阶段开启。
直觉会选"全局开"，那是错的。

**实现要点**：键用**两级 Map（`A → (B → gcd)`），键是 BigInt 本身**，
利用 gcd 对称性归一化成 `A ≥ B`。V8 对 BigInt 键直接做数值哈希，
完全跳过 `toString`。初版用 `a+':'+b` 字符串键，建键成本 `O(位数)`，是 lex 变慢的主因。

**fail-closed 约束**：所有早退分支（含 `nvars>6`、`groebner-failed`）都必须
`bgcdCacheEnable(false)` 清缓存。缓存绝不能跨求解残留。

## 4. 实根隔离（回代层）

### 4.1 两阶段架构

**核心思想：消元塔负责"找对候选"，Newton 负责"磨准"。**
不再为链尾会被 Newton 覆盖的精度长期支付 BigInt 成本。

| 阶段 | 方法 | 产出 |
|---|---|---|
| A 定位 | Sturm 序列浅层二分，桶宽 < `minSep`（1e-3） | 候选桶 |
| B 精修 | 桶内 Newton + 连分数有理化 | 精确有理根 |
| 认证 | 双重认证（见下） | 通过则采信 |
| 回退 | `fbExact` 纯精确深二分 | 认证失败时 |

### 4.2 双重认证 —— 完备性与正确性必须分开

| 认证 | 证明什么 | 手段 |
|---|---|---|
| **A：Sturm 计数** | 桶内的根**没漏** | `c1 + c2 === bk.n` |
| **B：精确有理残差** | 算出来的**确实是根** | `\|f(rat)\| ≤ amax·1e-9` |

> **关键教训**：Sturm 认证只能证明"没漏根"，**不能**证明"没算错根"。
> Newton 收敛到相邻错误根时，根数认证仍会通过，只有残差能识破。
> 只做 A 会漏掉"根数对、根错"这类错误 —— v9 实际踩过。

### 4.3 踩过的坑

1. **Newton 从桶中点出发收敛到错误相邻根**
   桶内只有 1 根**不保证**从桶中点出发 Newton 收敛到那根 —— 塔尖含重因子时导数穿过 0。
   修法：先用 Sturm 计数把桶收窄到约 1e-7；Newton 出界则中点阻尼；
   用 Sturm 计数守恒收缩（不依赖符号，故重根也安全）；最后加残差认证。

2. **包围盒收缩方向写反**
   根在左边时应丢右半、收缩右端点：`if (f > 0) { if (x < xr) xr = x; }`。
   改为 Sturm 计数守恒收缩后，从根本上不依赖符号方向。

3. **整根吸附候选边界比较对象写错**
   应该是 `rCmp(n, b) > 0`（桶右端），不是 `rCmp(n, SEP) > 0`。
   症状：quad4 从 14 解掉到 12 解 —— 负侧桶枚举到了另一个桶里的整数根。

4. **`feasTol` / `feasEps` 参数名不一致**
   `solveByTower` 传 `feasTol`，`uniSolveAll` 读 `feasEps` ⇒ 该值一直被静默忽略。

5. **哨兵值不能与合法值域重合（v10 新踩）**
   Lehmer 里用 `0n` 当"不适用"哨兵，但 `0n` 本身是合法 gcd 结果 ⇒ 87983 个用例失败。
   哨兵必须取**合法值域之外**的量（`null`）。

6. **BigInt 取模的符号约定（v10 新踩）**
   BigInt `%` 遵循"被除数符号"约定，负数取模可正可负。
   Euclid 循环里不取绝对值 ⇒ gcd 带符号返回 ⇒ 39241 个用例失败。

## 5. 已被实测否证的路线（别再试）

这一节比上面所有内容都值钱。**每一条都是"看起来很合理"的想法。**

### 5.1 整系数表示（clear_denoms 思想）—— v9.2 已否

**出发点**：profile 显示 `bgcd` 占 60.2%，推论"改成整系数就能消掉 gcd"。

**数学上完全正确**，在 `QQ[x]` 上整系数化确实精确等价。

**实测负收益**：

| 系统 | QQ 路径 | 整数路径 | 基大小一致 |
|---|---|---|---|
| quad3 | 3 ms, size 4 | 197 ms, size 5 | ❌ |
| quad4 | 10 ms, size 7 | 5282 ms, size 10 | ❌ |
| quad5 | 124 ms, size 11 | 9506 ms, size 13 | ❌ |
| quad6 | 4821 ms, size 18 | 11098 ms, size 14 | ❌ |

**为什么反而更慢**：
1. QQ 路径里绝大多数系数分母是 1，`bgcd(n, 1)` 几乎免费；
2. 整系数路径让分母累乘，系数变大，BigInt 乘法超线性增长；
3. `iAutoReduce` 是单遍，而 QQ `autoReduce` 多遍到不动点 ⇒ 基不完整。

**代码保留**在 `_p61_proto.cjs` 里作为记录，**不接入** `suan61Solve`。

### 5.2 Gebauer–Möller 安装准则 II —— v10 刚否

**第一次还写错了形式**：写成 `LM(h)[q] ≤ max(LM(h)[q], LM(g_k)[q])`，
这是**恒真式**，实测命中率 306/306 = 100.0%。
**一个恒真判据在任何数据上都显示 100%，这本身就是危险信号。**

改成正确形式（`∃m≠k` 使 `lcm(LM(h),LM(g_m))` 整除 `lcm(LM(h),LM(g_k))`）后，
quad6/lex 真实基上命中率 94.8%。

**仍然不上**，两个理由：
1. 94.8% 意味着几乎剪不掉东西 —— 剩下 144 对只能再剪掉约 7 对，收益 ≤ 2%；
2. **前提不成立**：GM-II 要求"基已完全约化"，但本实现 `autoReduce` 只在
   循环**结束后**才跑，循环中途 `G` 并非约化基。

**独立交叉验证**：构造随机首项做敏感度测试，命中率随指数范围剧烈变化
（0.0% / 33.3% / 66.7% / 100.0%），说明判据本身有真实内容、不是恒真；
但在 lex 塔这种"首项跨度大"的结构里它趋于恒真 ⇒ 无信息量。

### 5.3 移位二分求 BigInt 位长 —— v10 刚否

位长计算用 `toString(2).length` = 174 ns，而 `a >> 70n` = 34 ns，
直觉是"用移位应该快 5 倍"。

**实测**：`shift-binary bitLen` = **329 ns**，比 `toString(2)` **慢 89%**，
且实现有 932 处边界错误。

⇒ **`toString(2)` 保留。** V8 的 BigInt 右移不是廉价操作。

### 5.4 全局开启 gcd 缓存

见 §3.3。lex 阶段命中率仅 16.8%，全局开是净负收益。

### 5.5 Binary GCD（Stein 算法）—— v11 刚否

**出发点**：profile 显示 gcd 家族占 73.4%（Lehmer 41% + bgcd 27% + R 5.6%），
是唯一大头。Stein 算法（Knuth 4.5.2 Algorithm B）**只用移位和减法、零除法**，
理论上应比 Euclid 快——尤其 BigInt 除法比移位贵。

**实测（200k 次调用，64bit 随机奇数对）**：

| 算法 | ns/call |
|---|---|
| Euclid（现有，含 Lehmer） | **1919** |
| Stein（binary gcd） | **8588** |

**慢 4.5×。** 原因：V8 的 BigInt 右移 `x >> 1n` 每次都**新建一个 BigInt 对象**，
不是廉价的位操作；而 `%` 走内部快路径。⇒ 移位密集 ≠ 快。

**正确性已验证**（20000 组对拍，0 不等价），只是慢，不接入。

### 5.6 把 double 快路径阈值从 2^53 扩到 2^63 —— v11 刚否

**出发点**：实测发现 V8 BigInt `%` 在 64bit 处有**跳变**：

| 操作数位数 | Euclid ns/call |
|---|---|
| 48 bit | 282 |
| 56 bit | 303 |
| **64 bit** | **2212** |
| 72 bit | 3176 |

56→64 bit 是 **7.4× 跳变**（V8 从单字 BigInt 切到多字慢路径）。
若能把 2^53–2^63 区间也走 double 快路径，能吃掉一大块。

**实测否证**：在 (2^53, 2^62) 和 (2^62, 2^63) 各测 200000 组，
double-Euclid 与精确 BigInt-Euclid **全部不等价**（200000 / 200000 错）。

**原因**：`Number` 只能精确表示到 2^53，`a > 2^53` 时 `Number(a)` 已经失真，
后续 `x % y` 全是浮点近似。⇒ **2^53 是硬边界，与 IEEE754 binary64 精确整数上限一致，不可扩。**

### 5.7 模素数 Gröbner 基（modular Gröbner）—— v11 部分否，详见 §9

**出发点**：这是理论上对的方向。模素数下系数恒在 `[0, m)`，
若 `m < 2^26` 则乘积 `< 2^52 < 2^53`，**double 全程精确**，
128 bits 的 intermediate swell 被彻底消除。

**原型实测（`_p61mod.cjs`，m = 1000003）**：

| 系统 | QQ lex | 模 lex | 加速 | 模基元素 | QQ 基元素 |
|---|---|---|---|---|---|
| quad3 | 3 ms | 2 ms | 1.5× | 3 | 4 |
| quad4 | 5 ms | 1 ms | 5.0× | 3 | 7 |
| quad5 | 71 ms | 16 ms | 4.4× | 10 | 11 |
| **quad6** | **2653 ms** | **53 ms** | **50.1×** | 17 | 18 |

**但两个致命问题，让它不能接入**：

1. **素数必须 < 2^26**。实测 `m = 2^31−1` 时 quad6 **直接跑不出来**（基膨胀到不收敛），
   `m = 8388593 (~2^23)` 时 46 ms 正常。⇒ double 乘法的硬约束，不是保守设计。
2. **模基首项集是 QQ 基的严格子集，恰好缺 `1,0,0,…,0`（x₁ 的纯幂）那一层**。
   quad5 缺 1 个、quad6 缺 1 个，**其余首项逐项一致**。
   ⇒ 消元塔少一层，回代会漏解。
   这不是实现 bug，是**模运算的本质限制**：x₁ 那一层的系数是有理数（如 1/2），
   模运算**无法区分"有理的 1/2"和"无理的根"**，必须靠有理重构 + 符号判断才能定，
   那是完整 Modular Gröbner 的另一半工作量。

**更糟的是**：无 GM 时 quad6 模基**跑不完**（> 280 s）；
而加了 Gebauer–Möller 后 quad6 只需 53 ms —— 但**我的 GM 实现是错的**（见 §5.2 补充），
quad4 基从 6 元素塌到 3 元素，掉了整整两层约束。

⇒ **结论：模 Gröbner 是对的方向，但需要正确的 GM 增量剪枝 + CRT 有理重构才能落地。
本轮只做到原型，代码保留在 `_p61mod.cjs`（`useGM=false` 默认关闭），不接入 `suan61Solve`。**

### 5.8 补充：Gebauer–Möller 在模版里的实现错误（比 §5.2 更严重）

§5.2 否的是「GM-II 判据形式」；本轮在写模版时**又犯了一次同类错误**，
而且这次**后果是错的**（不只是没收益）。

我在**归约之前**用纯 lcm 整除关系剪 pair 队列。实测（m=1000003）：

| 配置 | raw 基 | 极小化后 | QQ 参照 |
|---|---|---|---|
| 无 GM | 12 | **6** | 7 |
| 有 GM（我的实现） | 6 | **3** | 7 |

⇒ 我的 GM 剪掉了 6 个 pair，其中**有必需的**，基从 6 塌到 3，**解集被放大**。

**错因**：GM 判据要求在 Buchberger 主循环里**增量**做 ——
每生成一个新元素，用它检查队列里已有 pair 的 S-多项式首项能否被整除。
我写成了「轮次开始时对整个剩余队列做 lcm 整除剪枝」，缺少链式条件前提。

**教训（比结论更重要）**：
> 剪枝类优化**必须用「基大小」而不是「耗时」作为正确性判据**。
> 本次若只看耗时，53 ms vs 2653 ms 会显示"50 倍成功"，我会直接接入并交付一个漏解的求解器。
> 是「首项集必须逐项对得上 QQ 基」这条断言把它抓出来的。

## 6. 性能实测数据

### 6.0 v11：pReduce 原地归约（本轮已落地成果）

**改了什么**（`_p61_proto.cjs`）：

1. **归约内层改为原地操作**。旧写法每步 `pSub(r, pMul(mono, g))` 要
   `copyPoly(r)` 全量深拷贝 + `pMul` 建 n×m 中间 Map + `pSub` 再建一次。
   但 `r` 一进来就是 `copyPoly(f)` 的**私有副本**，原地改绝无污染风险。
2. **`reduceCtx` 缓存首项系数** `lcs`。旧代码在归约内层每步 `pLead(g.list[hit]).c`，
   一次 `pLead` 是 O(项数) 全扫描 —— 18 元素 × 192 项 × 数千步 = 白烧。

**quad6 实测（三轮）**：

| 指标 | v10 | v11 | 提升 |
|---|---|---|---|

**实现中踩的两个坑（都写进了代码注释）**：

| 坑 | 症状 | 根因 |
|---|---|---|
| 先删首项再合并 | 归约死循环，立方耦合基塌成常数 −2 | `g` 的首项映射过去的键**正好等于**首项键（`hq + LM(g) = LM(r)`），先删后插会把它以非零系数塞回去 |
| else 分支漏负号 | 整个余式反号 | 归约是 `r ← r − fq·g`，"该键在 r 里不存在"时必须写入 `−contrib` 而非 `+contrib` |

**顺带修掉一个真隐患**：`_reduceCache` 的 key 只有 `(G 对象, G.length)`，
**不含 `CMP_MODE`**。若同一 G 在 grevlex 下建过缓存、之后切到 lex 再归约
（`buchbergerLex` 正是这么做的），会拿到 grevlex 序下的排序和首项 ⇒ **结果错且不报错**。
12/12 常规用例全绿也照样错，是对拍脚本交替 `setCmpMode` 才逼出来的。
现在 `CMP_MODE` 已并入 key。`lcs` 也改为**存值快照**（term.c 会被 `cur.c = s` 原地改写）。

## 8. 下一步（按实测杠杆排序，不是按直觉）

> v11 实测后的重新排序。**排序依据是实测数据，不是理论吸引力。**

**已排除的（实测否证，不要再考虑）**：
Binary GCD / Stein（慢 4.5×）、扩 double 快路径到 2^63（2^53 是硬边界）、
移位求位长（慢 89%）、整系数化（慢 2.3×）、全局 gcd 缓存（lex 负收益）。

1. **Modular Gröbner 基 —— 但必须先做对 GM 增量剪枝**
   原型已跑通（`_p61mod.cjs`），quad6 **53 ms vs QQ 2653 ms = 50×**。
   但卡在两处，都不是小修小补：
   - **GM 剪枝要重写**：现在的实现是错的（§5.8，基从 6 塌到 3）。
     正确做法是在主循环里**增量**做：每生成新元素就检查队列里已有 pair 的
     S-多项式首项能否被整除。没有它，quad6 无 GM 时跑不完（> 280 s）。
   - **CRT 有理重构**：模基恰好缺 `1,0,0,…,0`（x₁ 纯幂）那一层（§5.7）。
     x₁ 层的系数是有理数，模运算分不出"有理 1/2"和"无理根"，必须做有理重构。
     素数必须 `< 2^26`（double 乘法硬约束），13 个安全素数 ≈ 330 bits CRT 容量，够用。

   **这是唯一能追平档 1（只比 Gröbner 基）的路**，也是工业级 CAS 的标准做法。
   ⚠️ 工作量明确：GM 重写 + CRT 重构 + 消元塔层数校验，三个独立大工程。

2. **F4 / F5 矩阵化 Buchberger**
   把互不相关的 S-多项式批成矩阵，用线性代数批量约简。
   对 lex 这种"消元塔"结构尤其有效。**与路线 1 正交** —— 模算术解决系数膨胀，
   F4 解决 S-多项式个数，两者可叠加。

3. **减少回代层 `bisectNodes`（quad6 约 25000）**
   Descartes 区间树 / VAS 替换纯 Sturm 二分；缓存 `signVariations`。
   回代现占 3331 ms / 55%。
   ⚠️ 但 profile 显示 `signVariations` 只占 0.56%、`substituteExact` 0.34%
   ⇒ **瓶颈不在 Sturm 本身** —— 下一轮要先插桩定位再动手，别直接写 Descartes。

4. **suan61 接入主内核**（AST → `Poly` 转换尚未实现）

### 8.1 lex 基项数爆炸的结构诊断（已做，指向下一步）

lex 基元素的项数沿消元方向**单调爆炸**：

| 首项 | 项数 |
|---|---:|
| `x5^12`（塔尖） | 12 |
| `x4²` | 4 |
| `x3²x5^8` | 47 |
| `x2²x5^8` | 101 |
| `x1 x5^8` | **192** |

最大基元素（192 项）的变量幂次分布：
`x1¹`（8/192 项）、`x2³`（100/192）、`x3⁵`（106/192）、`x4⁴`（103/192）、`x5⁹`（138/192）。

⇒ **这不是数值膨胀，是代数上必需的**：塔尖 `x5` 的消元多项式本身是 12 次、18 次
（对称性导致高次幂），不可约。
⇒ 所以不能靠"减少精度"省时间，只能靠 **modular 算术把系数从 BigInt 换成机器字**。

### 8.2 方法论：本轮抓到的三个"假成功"

写在这里，因为它们比性能数字更值钱。

| 假象 | 真实情况 | 怎么抓到的 |
|---|---|---|
| GM 剪枝让 quad6 从 2653 ms 变 53 ms | 基从 6 塌到 3，**漏掉两层约束** | 断言"首项集逐项对得上 QQ 基" |
| v11 原地归约后 37/48 通过，剩 11 个"小 bug" | 其中一个是**整个余式反号** | 3971 组逐项对拍 |
| `reduceCtx` 缓存 12/12 用例全绿 | 跨单项式序复用会给出**错的归约结果** | 对拍脚本交替 `setCmpMode` |

**共同点**：性能优化让数字变好看，**正确性断言让数字变诚实**。
剪枝类改动必须用「基大小 / 首项集」而不是「耗时」当判据；
重构算术后必须做逐项对拍，不能只跑回归用例集。
