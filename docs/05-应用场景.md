# 05 · 应用场景

> 它能在哪些地方真正派上用场、怎么接、能拿到什么、什么情况下**不该**用它。
> 接入方式统一是 MCP（本地 stdio 或远程 HTTP），场景差异只体现在"谁调用、拿结果做什么"。

---

## 〇、先给判据：什么时候该用它

满足下列**任意两条**，这个工具就有价值：

1. **结果要可复现** —— 同一输入必须给出同一答案（否则无法缓存、无法审计、无法回归测试）。
2. **算错要承担后果** —— 结果进入定价、风控、报表、仿真收敛判据等下游环节。
3. **需要"这个数算对了"的凭证** —— 结果要能被人或另一套系统独立校验，而不是"另一个模型也说对"。
4. **数据不能出域** —— 方程本身就是业务信息，不能发到外部服务。

反过来，如果只是"帮我把这个式子化简一下""给我推导一下这个公式"，那需要的是符号 CAS，不是它。

---

## 一、AI Agent 的数学后端（最常见、最先落地）

**痛点**：让 LLM 自己算数学，它会一本正经地编造数字；同一个问题问两次可能得到两个答案。
Agent 的推理链只要中间有一个数字是编的，下游全错。

**怎么接**：把 `solve` 挂进 Agent 的工具集（MCP 一行配置，见 [02 · 使用指南](02-使用指南.md#三ai-agent-接入mcp)）。

**典型调用**：

```json
{ "equations": ["2x + 3y = 12", "x - y = 1"], "domain": { "x": [-100, 100], "y": [-100, 100] } }
```

**得到什么**：结构化解 + `certified: true` + 认证半径 + 回代残差。
Agent 可以把"我算出来"换成"我调用了认证求解器，结果是这个，这是凭证"。

**注意**：
- 方程**必须每条独立成数组元素**（整串塞一个元素会解出 0 解）。
- 遇到 `truncated: true` 时把它如实告诉用户（"可能还有解，但我没法证明穷尽了"），别当完整答案用。

---

## 二、多 Agent 协作中的可信中间结果

**痛点**：A Agent 算出一个数交给 B Agent 用，B 只能"相信"。
一旦 A 用 LLM 算的，整条链的可靠性等于最弱一环。

**怎么接**：把 `solve` 作为**中立第三方节点**，各方只信"经认证的结果"而不信对方的算术；
认证字段（`certified`、`tier`、`certifiedRadius`）本身就是可传递的凭据。

**得到什么**：一份"这个数确实满足方程"的可校验凭证，可随消息一起传递、由任一方独立复核。

**注意**：凭证证明的是"该解满足给定方程且经区间验证"，**不证明方程本身建模正确**——
方程建错了，认证会把错方程解对。

---

## 三、链下计算 / 需要可验证计算凭证的场景

**痛点**：某些链路要求"链下算、链上信"，但"重算一遍"成本高，"盲信"风险大。

**怎么接**：把求解作为链下计算步骤，输出附带认证字段，作为可验证凭证留存。

**得到什么**：确定性 + 可复现 ⇒ 任何人拿同样的输入重跑能得到**逐位相同**的结果和同样的认证结论。

**注意**：它是**确定性可复现**，不是密码学零知识证明。别把它当成 zk 方案。

---

## 四、财税 / 风控 / RPA 的校验层

**痛点**：自动化流水线里有一批"必须算准"的中间量（分摊系数、利率反解、限额配平、对账勾稽），
算错会直接变成错账或误判。

**怎么接**：流水线每个计算点调一次 `solve`，按认证结果分流：
**认证通过 → 自动过账；未认证 / `truncated` → 转人工复核**。

```
计算请求 → solve → certified? ──是──▶ 自动过账（附认证凭证入日志）
                        │
                        └─否──▶ MANUAL_REVIEW 队列（附诊断信息）
```

**得到什么**：一个 fail-closed 的闸门——不确定时不放行，而不是"猜一个数进了账"。

**注意**：本产品是数学计算工具，**不构成**财税、审计或法律结论；请把它当计算与校验组件，
结论与合规责任仍在使用者一侧。

---

## 五、企业私有化 / 内网嵌入

**痛点**：很多行业（金融、制造、医疗、政务）不允许把业务参数发到外部服务，
但内部又缺一个可靠的方程组求解能力。

**怎么接**：
- 直接 `npx -y lingshu-solver`（本地 stdio，离线零外发）；
- 或自托管 `http-mcp-server.js`（`PORT=3000 node http-mcp-server.js`），
  **计费默认关闭**，内网部署即为内部服务（部署与配置见 [02 · 使用指南](02-使用指南.md#六自托管远程-http-形态)）。

**得到什么**：数据不出域、零第三方依赖（供应链干净）、可进离线环境、可被内部系统与 Agent 同时调用。

**注意**：自托管时请自行配置 nginx 安全头与限速；管理端点保持默认的"回环 + 令牌"双锁。

## 六、教育与自学

**痛点**：学生/自学者用 LLM 问数学题，得到的是一个"看起来对"的答案，无法自检。

**怎么接**：网页版直接打开用（<https://hongchenlingjing.com/>），或用本地版接到自己的笔记/工具链里。

**得到什么**：
- 答案是确定的，可反复复现，便于对照作业与教材；
- 每个解都能**回代验证**（把解代回方程，看左右两边是否相等）——这本身就是很好的学习动作；
- 解不出来时它会说明是"证明无解"还是"预算内没算完"，而不是随便编一个。

**注意**：它不是解题步骤讲解器（不做符号推导），讲思路仍需人或教材。

## 七、审计与合规留证

**痛点**："这个数字当时是怎么算出来的"在事后往往无法复现——
模型版本变了、随机种子变了、库升级了，结论就再也回不去。

**怎么接**：把 `solve` 的完整响应（含 `diagnostics.solverVersion`、认证字段、诊断信息）
随业务日志一起入库。

**得到什么**：事后可复现的计算凭据（输入 + 版本 + 认证结论 + 残差），
只要版本与输入在，结果就能被任何人重跑出来。

**注意**：留证时请同时记录 `diagnostics.solverVersion`——版本是复现的前提（见 [08 · 版本管理](08-版本管理.md)）。

## 八、明确不适合的场景（省得白试）

| 场景 | 为什么不适合 | 该用什么 |
|---|---|---|
| 符号推导、闭式解、公式化简 | 它是数值求解器，不做符号运算 | SymPy / Mathematica 等 CAS |
| 微分方程（ODE/PDE） | 不同的数学问题 | 专门的 ODE/PDE 求解器 |
| 整数规划 / 丢番图约束 | 不支持整数强制（会报 `integer-unenforced`） | MILP/CP 求解器 |
| 高精度科学计算（多精度、大矩阵） | 固定 6 位小数有限网格 | MPFR/GMP、专业数值库 |
| 大规模优化（千变量级） | 变量上限 6 | 专业优化器 |
| 金融投资 / 医疗诊断结论 | 它是计算工具，不构成专业结论（合规红线） | 相应持牌专业判断 |
| 想"100% 保证不漏解" | 一般情形下数学不可判定，任何实现都做不到 | 限定输入类的问题专用算法 |
