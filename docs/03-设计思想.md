# 03 · 设计思想

> 本文说明这个产品**为什么这样设计**：六条原则、可信度的来源、刻意的取舍、以及有意不做的事。
> 想看"怎么实现"请看 [04 · 技术参考](04-技术参考.md)。

---

## 一、六条设计原则

### 原则 1 · 确定性优先于"更聪明"

**做法**：核心是一条纯算法流水线，不含任何神经网络、不含随机分支、不含启发式温度。
相同输入永远返回逐字节相同的结果。

**为什么**：需要数学结果的系统，最怕的不是"算不出来"，而是"这次算出来是这样，下次是那样"。
不可复现的结果无法缓存、无法审计、无法作为下游决策的依据。
大模型在数学上的优势（覆盖面广）与它的致命缺陷（会编造）是同一件事的两面——在这个产品要解决的问题上，缺陷远重于优势。

**体现在代码里**：无 `Math.random()`、无时间相关的分支、无外部状态；同一份核心被三种形态复用。

### 原则 2 · 可验证优先于"看起来对"

**做法**：不只给数值，还给**认证**。每个解带 `tier`（`proven`/`candidate`）、`certified` 标记与
认证半径 `certifiedRadius`，并附回代残差 `residual`。

**为什么**：一个数字本身无法自证。给它盖一个"经区间运算验证过"的章，
调用方（人或 Agent）才能把"信任"从"相信这个软件"转移到"相信这个数学事实"。

**体现在代码里**：Krawczyk 算子做不动点构造性认证；无法认证的候选点被降级为 `candidate` 并明说，
**绝不与 `proven` 混同**。

### 原则 3 · 诚实降级优先于假装完整

**做法**：三种失败/降级都显式暴露，而不是吞掉：
- 预算内未证明穷尽 ⇒ `truncated: true`
- 输入不合法 ⇒ `diagnostics.inputError` 明确指明（且不计费）
- 无法认证的解 ⇒ `tier` 降级
- 内部异常 ⇒ 结构化错误类型，且**绝不泄露内部堆栈**

**为什么**：这是本产品最重要的商业资产。买方愿意为"它不乱说"付钱；
一旦系统在不确定时也输出一个看似正常的答案，整条信任链就断了。
**fail-closed 的含义是：不确定就拒绝或降级，而不是猜一个。**

**体现在代码里**：`resultType` 三态严格区分"证明无解"与"没找到"；
`provenEmpty` 只在有严格依据时置位；`integer-unenforced` 这类"不满足但你该知道"的警告一定上报。

### 原则 4 · 离线、零依赖、零数据

**做法**：核心与两种服务端只用 Node 标准库与浏览器标准 API，**零第三方依赖**。
网页版在浏览器内完成计算；本地版不联网；托管端点只记元数据、不落盘方程内容。

**为什么**：
- **隐私**：方程往往就是业务信息（定价公式、风控阈值、仿真参数），不该因为"要用一个工具"而外发。
- **可部署**：零依赖意味着能进内网、进离线环境、进审计严格的机房。
- **供应链安全**：没有第三方包就没有第三方漏洞面。

### 原则 5 · Agent 原生

**做法**：把产品当成 MCP 工具设计，而不是"先做网页，再包一层 API"。

**为什么**：Agent 不会读落地页，**它只读 `tools/list` 返回的 `name` + `description` + `inputSchema`**。
工具描述就是它决定"该不该调、怎么调、结果怎么读"的唯一说明书。
所以描述必须详尽、诚实、含使用契约（硬限制、结果语义、错误语义、免费路径）。

**体现在代码里**：`solve` 的 `description` 写全了能力边界、硬限制与字段语义；
`give_feedback` 让 Agent 能主动回报卡点；撞到计费墙的响应里**必须带免费路径**——
否则 Agent 只会放弃调用，用量与转化一起丢。

### 原则 6 · 克制：没有信号就不扩张

**做法**：不因为"技术上能做"就加功能。低频或易引入歧义的特性（双曲/反三角、ODE、整数强制）
**明确不做，并在文档里列为已知限制**。

**为什么**：每加一个特性就增加一类边界情况、一个潜在的不诚实点、一份测试成本。
在一个以"可信"为卖点的产品上，"少而可靠"优于"多而模糊"。

## 二、可信度从哪来（数学直觉 + 严格性）

### 2.1 区间算术：把"误差"变成"范围"

普通浮点运算给你一个数 `2.4`，但你不知道它离真值多远。
**区间算术**给你一个区间 `[2.399999..., 2.400000...]`，并且保证**真值一定落在其中**
（舍入方向受控，包络性质不被浮点误差破坏）。

由此得到一个关键能力：
> **如果某个变量或表达式的区间包络不含 0，就严格证明了"这个盒子里没有解"。**

这不是"没找到"，是**证明不存在**。产品里的 `empty`（无解）结论正是靠这一点成立的。

### 2.2 收缩算子：把搜索空间"挤"到解附近

盒子在搜索中被反复收缩：保留必然含解的部分、剔除必然无解的部分。
本产品用了 HC4-Revise、约束反演（项一致性）、Box-Consistency（BC3/2B/3B）、
Hansen-Sengupta 区间 Gauss-Seidel、LP Narrowing 等经典算子（共 6 个主力收缩算子，见 [04](04-技术参考.md)）。

### 2.3 Krawczyk 认证：给解盖章

收缩到足够小之后，用 **Krawczyk 算子**做不动点构造性验证：
它能证明"该区域内**存在唯一解**"，并给出误差半径。
通过认证的解标 `tier = proven` —— 这就是"盖章"的严格含义：
**不是"我算得挺准"，而是"在这个模型与精度下，解的存在性与误差上界已被证明"。**

### 2.4 全局搜索：尽力而为，并且承认边界

`全局分支定界` 把域递归二分，配合收缩算子剪枝，力求找全所有解。
但必须诚实说明一条数学事实：

> 对一般的非线性方程组，**"保证找到全部解"是不可判定的**（与 Richardson/Smale 意义下的判定问题相关）。
> 任何声称"保证不漏解"的实现，要么限制了输入类，要么在说谎。

因此本产品的口径是 **「已验证解数学保真 + 全局穷尽尽力而为」**：
能证的就证，证不了的就标 `truncated` 让你自己决定是否加大预算。这是设计选择，不是缺陷。

### 2.5 为什么不让大模型来"理解"方程

输入归一化（Unicode 符号、竖排换行、隐式乘法、`log2`/`log10` 识别）全部由**确定性规则**完成，
不用 LLM"猜用户想写什么"。

理由：LLM 在这一步的容错率看似更高，但它会引入不可复现的歧义——
同一个输入今天被理解为 `x^2`、明天被理解为 `x*2`，这在数学工具里是不可接受的。
**宁可让用户补一个括号，也不让结果不可复现。**

## 三、结构：单一真源 + 多形态

```
        index.html 内的 <script id="solver-core">   ← 唯一真源（求解内核）
                        │
      ┌─────────────────┼─────────────────┐
 solver-core.js    mcp-server.js    http-mcp-server.js
  （vm 加载器）      （stdio 形态）    （streamable-http 形态）
      │                 │                 │
   npm 包 / 网页     本地 MCP 进程      线上 /mcp 端点
```

**为什么把内核放在单文件 `index.html` 里**：网页版必须"双击即用、零构建"；
同时 MCP 与测试要复用同一份算法。于是内核以 `<script id="solver-core">` 的形式内嵌，
由 `solver-core.js` 用 `vm` 抽取给 Node 使用——**同一份代码，三种形态，不可能出现"网页版和 MCP 结果不一致"**。

**代价（如实说明）**：内核改动后必须重启服务（`vm` 沙箱已加载旧代码），且改内核要同时更新线上两份 `index.html`。
这条代价我们接受，因为它换来的是"只有一个真源"。

## 四、刻意的取舍（以及为什么）

| 取舍 | 选择 | 理由 |
|---|---|---|
| 精度 | 固定 6 位小数，不做位数切换 | 有限网格让结果可比较、可缓存、可复现；也避免"多一位小数看起来更专业"的伪精度 |
| 默认域 | ±1e6，但允许显式 `domain` | 兼顾"不填也能算"与"病态场景可控"；快增长函数必须显式给域，文档里明说 |
| 变量数上限 | ≤ 6 | 分支定界的复杂度随维数爆炸；与其在高维给出不可信结果，不如限制范围并保持诚实 |
| 计费 | 托管端点固定 ¥0.01/次 + `honorPaid` 免费放行 | 见 [06](06-商业授权与收费.md)。**它是定价信号，不是商业模式**；不设套餐、不预充，避免把用户挡在门外 |
| 许可 | 非商业免费 + 商业须书面授权 | 让个人与教育场景零摩擦使用，同时让商业使用回到合同与发票体系 |
| 端点形态 | 只走 MCP（HTTP + stdio），不额外造 REST SDK | 生态位是"Agent 的工具"；多一套 SDK 就多一份维护与口径不一致 |

## 五、有意不做（明确记录）

| 不做 | 原因 |
|---|---|
| 双曲 / 反三角函数（`sinh/cosh/tanh/asin/acos/atan`） | 易与隐式乘法规则冲突、低频需求；诚实列入已知限制而非模糊支持 |
| 整数 / 自然数强制约束 | 需要混合整数求解框架，与当前区间连续求解路线不同；现以警告 `integer-unenforced` 明示 |
| 微分方程（ODE/PDE） | 是不同的数学问题，需要不同数值框架 |
| 符号推导 / 闭式解 | 与"数值认证"是两条路线，混在一起会两边都不专业 |
| "必不等于"约束 | 语义在连续求解中易歧义，暂无可靠实现 |
| 把输出包装成金融/医疗/法律结论 | 本产品是数学计算工具，不构成任何专业领域认证（合规红线） |
| 公开的自助充值门户 | 定位与合规共同决定：对外定性"软件授权 / 技术服务"，商用走合同与年授权（见 [06](06-商业授权与收费.md)） |

## 六、一句话总结设计立场

> **不追求"什么都能算"，追求"算出来的每一句都站得住"。**
> 能力边界写清楚，比能力边界更大更重要。
